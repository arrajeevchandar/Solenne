Solenne is two independent apps that share no code — a Flutter client and a Python analyzer worker. There is no HTTP API between them: Firestore is both the job queue and the message bus, and Cloudinary is the media store.

The client writes a journal and a queued job in a single transaction; the worker polls, claims, analyzes and writes results back to the same document; the client is listening on a live snapshot stream and updates itself the moment processing completes.

Two invariants carry deliberate visual weight — the grounding boundary (only transcript-derived signals may trigger a research claim) and the release-controlled catalog (no live web research during processing).

4Grounding boundary

The one structural rule in the system — enforced in code, not by convention.

retrieve_claims only counts facts whose kind is topic or key_phrase. Voice, face and fused affect metrics have no code path to a research claim at all — the boundary lives in the retriever (grounding/retriever.py:20), not in prompt instructions.

5Catalog governance

Release-controlled and offline. Every citation traces back to a human-reviewed catalog entry.

The catalog stores sources, exact display claims, limitations, support levels and approved suggestions. No source text is ever copied at runtime, and no live web research happens during journal processing.

6Insight generation and fallback ladder

The crisis check runs first and bypasses ordinary AI generation entirely.

Three rungs on the fallback ladder:

  1. Two generate/validate attempts against the LLM.
  2. A deterministic grounded card that still carries a real citation.
  3. A user-data-only card, with no citation.

Rung 2 is deliberately skipped when the LLM was never reachable, so a bare template never gets a citation attached to it.

Groq drafts language only — title, summary, themes, mood, questions and allowed IDs. The server injects exact evidence values, catalog claim text, approved suggestions, limitations and canonical HTTPS citations. Validation then checks that no IDs were fabricated, no values altered, and catalog text is byte-identical.

Notes on accuracy

Details that are easy to get wrong, verified against the code.

  • Face analysis uses OpenCV Haar cascades, not MediaPipe (pipeline/face.py). backend/README.md still says MediaPipe and is out of date.
  • Four runtime modes exist, not three. combined serves narrative and grounded cards side by side and is what backend/.env.example ships today.
  • Claim limits differ by stage: the retriever supplies up to 3 claim cards to the model (runtime.py:94), while the assembler renders at most 2 citations per insight card (assembler.py:34).
  • The grounding boundary is structural. Voice, face and fused metrics have no code path to the retriever at all.
  • analysis_jobs/{journalId} uses the journal ID as its document ID, and the client may only ever create that document with status == 'queued'; all later job writes come from the Admin SDK worker.
